# 저장 성적검증의 결과 저장 최적화

## 변경 범위

성적 산출 결과를 저장하는 경로와 작업 진행 표시를 변경한다. 계산기, 전형·학과 매칭,
반영 과목 선택, 등급 환산, 소수점 처리, 미산출 판정과 업로드 판독기는 변경하지 않는다.
기존 데이터로 다시 성적검증을 실행할 수 있으며 원자료 재업로드나 스키마 변경은 필요하지 않다.

기존에는 산출 성공 때마다 `INSERT ... SELECT`를 한 번씩 실행했다. 새 저장 버퍼는
최대 200행 또는 보수적 UTF-8 추정 크기 512KiB를 기준으로 결과를 모은다. 한 행 자체가
한도를 넘으면 그 결과를 자르지 않고 단독 저장한다. 상세 JSON은 기존 직렬화 결과 그대로 저장한다.

각 묶음마다 지원정보 ID와 학생 ID의 관계를 한 번에 조회한 뒤, 매개변수를 사용한
단일 `INSERT ... VALUES (...), (...)`로 기록한다. JDBC URL의 batch rewrite 설정에 기대지 않는다.
관계가 누락되거나 저장 행 수가 다르면 실패한다. 명지 ZIP 미산출 사유 갱신도 JDBC 묶음 처리한다.

전체 결과 교체의 기존 트랜잭션 범위는 유지한다. 일부 묶음의 쓰기가 실패하면 삭제·새 결과 저장을
모두 롤백한다. 진행 정보의 저장 처리 건수는 확정 전 건수이며, 작업 완료 상태는 트랜잭션을
적용하는 서비스 호출이 정상 반환한 뒤에만 설정한다.

## 진행 정보

기존 작업 조회 API에 `progress`를 추가한다. 단계와 전체 대상 수·저장 처리 건수·미산출 건수만
표시하며 수험번호, 성명, 개별 점수는 담지 않는다. 자료를 읽기 전에는 전체 건수를 모른다.
실패 판정의 합계는 기존 계산기가 반환된 뒤 확정되므로 산출 중의 미산출 0건을 최종 값으로
해석하면 안 된다. 화면은 미산출 건수가 확인된 경우에만 표시한다.

조회 단계는 `QUEUED`, `LOADING_INPUTS`, `PREPARING_SAVE`, `VERIFYING_AND_SAVING`,
`FINALIZING`, `COMMITTING`, `COMPLETED`다. 삼육 시나리오의 기존 저장 경로는 유지하며
해당 진행 단계는 `VERIFYING_SCENARIOS`로 표시한다. 구버전 응답의 진행 정보 누락도 허용한다.

## 검증과 적용

- 가상 결과 20,000건에서 200행짜리 쓰기 호출 100회를 검증한다. 실제 DB 왕복에는 묶음별
  관계 조회도 포함된다. 실제 JSON이 크면 크기 제한 때문에 묶음이 작아진다.
- 단위 테스트에서 결과 객체·JSON 문자열·순서·점수 필드·null 평균의 보존, 나머지 묶음 저장,
  큰 결과의 단독 저장, 쓰기 실패 전파 및 완료 전 진행 상태를 검사한다.
- 격리된 Testcontainers MySQL 테스트는 구 저장 경로와 새 경로의 결과를 비교하고,
  중복 키로 실패한 교체 작업이 기존 결과를 보존하는지 검사한다. Docker가 없으면 건너뛴다.
- 실제 지원자 데이터와 운영 DB로 속도나 점수 일치 여부를 측정한 것은 아니다.

백엔드와 프런트 변경을 함께 반영한다. 실행 중인 검증이 있으면 종료 후 백엔드를 재시작한다.
이미 진행 중인 작업에는 새 버퍼가 적용되지 않으며, 다음 검증부터 적용된다. 원자료 재업로드는
필요하지 않다. 전체 과목 입력을 메모리에 읽는 기존 구조와 JSON의 총 저장 용량은 그대로다.

## 이번 개발 환경의 확인 결과

전체 main/test 소스 직접 컴파일과 JUnit 대체 실행에서 단위 테스트 484개가 성공했고 1개는
건너뛰었다. Gradle wrapper는 기존 환경의 `Unable to establish loopback connection` 오류로
시작하지 못했다. 격리 MySQL 테스트 2개는 Docker가 없어 건너뛰었다. 이 결과를 운영 DB에서의
시간 단축률이나 전체 통합 검증 성공으로 해석하지 않는다. 실제 지원자 파일·운영 DB·실행 중인
작업은 조회하거나 재실행하지 않았다.

## 검증 계산 경로의 추가 최적화

- 같은 전형명·모집단위명의 규칙 탐색 목록을 검증 실행 안에서 재사용한다. 키는 원문 두
  문자열이며 한 실행이 끝나면 폐기한다. 다음 실행은 게시 규칙을 다시 조회한다.
  지원자의 과목·점수는 계속 개별 계산하며 전형 매칭 조건이나 규칙 우선순위는 바꾸지 않는다.
- 명지 ZIP의 동점자 보조값과 엑셀 요약에서 함께 쓰는 중간 집계를 한 번만 생성한다.
- DB 저장 전용 호출은 저장 후 쓰지 않는 과목 비교 목록·엑셀 중간값 목록을 유지하지 않는다.
  저장 콜백에는 기존과 같은 전체 계산 결과를 넘기므로 JSON의 상세 과목·원문·경고·보조값은
  그대로 보존한다. 미리보기·엑셀 내보내기의 상세 목록은 계속 생성한다.

산식, 학기 선택·동률 처리, 이수단위, 환산표, 반올림, 등급 확인 필요 판정, 미산출 사유는
변경하지 않았다. 프런트·DB 스키마·업로드 형식도 이 추가 변경의 대상이 아니다.

추가 검증에서 main/test 전체 소스 직접 컴파일 및 단위 테스트 488개 성공, 1개 건너뜀을
확인했다. Gradle은 같은 loopback 환경 오류가 남아 있어 대체 실행을 사용했다.
변경 전 소스를 별도 클래스 이름으로 보존한 로컬 비교에서는 2026·2027년, ZIP 메타데이터
포함·미포함의 가상 지원자 400명에 대해 기존 내보내기 결과와 새 내보내기 결과가 같았고,
저장용 전체 JSON·점수·경고·보조값·실패 사유도 같았다. 두 경로의 BigDecimal 값과 스케일,
과목 순서 및 선택 내역도 함께 비교했다. 구 버전 코드 복제본은 제품 소스에 포함하지 않는다.

가상 지원자 2,000명·과목 42,000행으로 워밍업 후 5회 측정한 계산 구간 중앙값은 변경 전
139.231ms, 변경 후 저장 전용 경로 136.487ms였다. 규칙 매칭 호출은 6,400회에서 16회,
보관하는 선택 과목 비교 항목은 14,400개에서 0개로 줄었다. 이 측정은 DB 입출력과 JSON
직렬화를 제외하며 실제 자료 처리시간이나 보장되는 개선율을 뜻하지 않는다. 입력 과목 전체를
읽는 구조는 유지한다. 같은 실행 안의 중복 작업과 불필요한 결과 목록만 줄인 변경이다.

기존 업로드를 다시 저장할 필요 없이 백엔드 재시작 후 다음 검증부터 적용된다.
